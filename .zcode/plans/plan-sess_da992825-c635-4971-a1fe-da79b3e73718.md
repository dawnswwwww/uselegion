## 目标
收到飞书消息后给该消息打 👀 表情表示"正在处理",回复发送后移除该表情。

## 现状
- **入站侧已就绪**:`channel_inbound.rs:116-126` 收到消息后 `tokio::spawn` 调 `add_reaction("👀")`,且飞书 `capabilities().reactions = true`,会被触发。
- **缺口 1**:`LarkProvider` 未实现 `add_reaction`,走 trait 默认空实现 → 飞书端没表情。
- **缺口 2**:trait 根本没有 `remove_reaction` 方法,channel_inbound 也从未移除表情。
- **飞书 API**:添加 `POST /im/v1/messages/{message_id}/reactions` body `{reaction_type:{emoji_type}}` 返回 `data.reaction_id`;删除 `DELETE /im/v1/messages/{message_id}/reactions/{reaction_id}`。

## 方案:Provider 内部存 message_id→reaction_id 映射(已确认)

### 改动文件
1. `crates/legion-plugin-sdk/src/channel.rs` — trait 新增 `remove_reaction` 默认方法
2. `crates/legion-channel/src/lark.rs` — 实现 add_reaction + remove_reaction + 内部映射
3. `crates/legion-host/src/channel_inbound.rs` — 收消息 await 打表情、回复后移除

### 步骤 1:trait 新增 `remove_reaction`(`channel.rs`)
在 `add_reaction` 后加默认空实现:
```rust
/// Remove a previously added reaction. Default: no-op.
async fn remove_reaction(
    &self,
    _peer: &Peer,
    _message_id: &str,
    _emoji: &str,
) -> Result<(), ChannelError> {
    Ok(())
}
```
签名用 `(peer, message_id, emoji)` 而非 reaction_id —— 让 Provider 自己内部按 message_id 找回 reaction_id。这样 channel_inbound 不需要知道 reaction_id 的存在。

### 步骤 2:LarkProvider 实现 + 内部映射(`lark.rs`)
- `LarkProvider` 加字段 `reactions: Mutex<HashMap<String, String>>`(message_id → reaction_id)。
- `add_reaction`:
  - `POST {base}/im/v1/messages/{message_id}/reactions`,body `{ "reaction_type": { "emoji_type": emoji_to_type(emoji) } }`。注意飞书用的是 emoji_type 名(如 `EYES`),不是 Unicode 👀,需做映射(👀→`EYES`)。
  - 解析返回的 `data.reaction_id`,存入 `reactions` 映射(key=message_id,同一消息只保留一个)。
  - 成功打 `info!` 日志。
- `remove_reaction`:
  - 从映射取出 reaction_id,`DELETE {base}/im/v1/messages/{message_id}/reactions/{reaction_id}`。
  - 删除后从映射移除(无论成功失败)。
- emoji 映射:写个小 helper `fn lark_emoji_type(emoji: &str) -> &str`,`👀` → `"EYES"`,其它原样返回(防御)。

### 步骤 3:channel_inbound 改为 await + 移除(`channel_inbound.rs`)
当前 `add_reaction` 是 `tokio::spawn` fire-and-forget(`:121-125`)。改为:
- **不在 spawn 里 fire-and-forget**,而是把 add_reaction 放进后续 `tokio::spawn(async move { ... 整个 run ... })` 的开头(await,因为 run 本身就是 spawn 的)。这样 reaction_id 在 Provider 内部就位后,run 结束 send 成功后调 remove_reaction。
- 在回复发送**成功**后(`provider.send(outbound)` 的 Ok 分支),调 `provider.remove_reaction(&peer, &message_id, "👀")`,失败仅 warn。
- 复用现有 `message_id` 变量(已 clone 到 spawn 作用域)。
- 注意:capabilities 检查保留(只在 `reactions == true` 时执行 add/remove)。

### 步骤 4:测试
- `lark.rs`:add_reaction 构造请求体、remove_reaction 删除路径(参考 telegram 的 `add_reaction_posts_set_message_reaction` 模式,用 wiremock 或断言 URL/payload)。若 lark 无 HTTP mock 基础设施,至少加 emoji 映射的纯函数单测。
- `channel.rs`:trait 默认实现编译验证。
