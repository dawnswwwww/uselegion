# Lark/Feishu 配置后链接校验

## 目标
在 `legion-cli` 的 setup 向导里，Lark 配置完 `app_id`/`app_secret` 后，**立即做一次真实连接校验**（取 tenant_access_token + 取 bot 信息），失败时给「重试 / 仍保存 / 放弃」三选项。参考 `larksuite/openclaw-lark` 的 `probeFeishu()` 思路，但用飞书公开 API（`/bot/v3/info`），不用 openclaw 私有的 `/bot/v1/openclaw_bot/ping`。

## 关键约束（已确认）
- **legion-cli 不依赖 legion-channel**（刻意分层，与 gateway 解耦原则一致）。探针逻辑放 `legion-cli` 内部，**不**改 `legion-channel`，**不**加 crate 依赖。
- 探针用 `reqwest`（已依赖）+ `serde_json`（已依赖），10s timeout（对齐现有 `test_connection` setup.rs:678）。
- 飞书凭据校验标准链：① `POST /open-apis/auth/v3/tenant_access_token/internal`（校验 appId/appSecret/app 状态），② `GET /open-apis/bot/v3/info`（校验 bot 就绪 + 拿 open_id/名称）。两步均走 `{base_url}`。
- 不做「发测试消息等回调」——setup 阶段无 gateway 运行，等不到 WS 回调；主动 probe 是无副作用、可重复的标准做法。

## 改动 1：`crates/legion-cli/src/setup.rs` — 新增探针 + 类型

在文件现有 `test_connection` / `TestOutcome` / `maybe_test_connection`（setup.rs:659-1484，model provider 用的那一套）**附近**新增平行的 Lark 探针：

### 1a. 探针结果类型（仿 `FeishuProbeResult`，openclaw `types.ts:134`）
```rust
/// Outcome of probing Lark/Feishu app credentials during setup.
#[derive(Debug, Clone)]
struct LarkProbeOutcome {
    ok: bool,
    /// 透传给用户的失败原因（飞书 msg / 网络错误）。ok=true 时为 None。
    error: Option<String>,
    /// 校验成功时顺带拿到的 bot 名称（来自 /bot/v3/info）。
    bot_name: Option<String>,
    /// 校验成功时顺带拿到的 bot open_id（用于回填 config）。
    bot_open_id: Option<String>,
}
```

### 1b. 探针函数 `probe_lark(app_id, app_secret, base_url) -> LarkProbeOutcome`
约 50 行，逻辑：
1. `reqwest::Client::builder().timeout(10s).build()`，失败 → `Failed("failed to build HTTP client")`。
2. **第一步**：`POST {base_url}/open-apis/auth/v3/tenant_access_token/internal`，body `{app_id, app_secret}`。解析 JSON：
   - `code != 0` → `Failed(msg)`（飞书返回 `app secret is invalid` / `app not published` 等具体原因）。
   - 取 `tenant_access_token` 字段，缺失 → `Failed(...)`。
3. **第二步**：`GET {base_url}/open-apis/bot/v3/info`，`Authorization: Bearer {token}`。解析：
   - `code != 0` → 这里降级为 **warning**（token 已证明凭据有效，bot 信息失败常因「bot 能力未开启」或权限未授权，不阻塞）。返回 `ok=true` 但 `bot_name/bot_open_id=None`，error 记一条提示给用户。
   - 成功 → 从 `data.bot` 取 `open_id` 和 `app_name`，填进 `LarkProbeOutcome`。
4. 网络层错误（`reqwest::Error`）→ `Failed(format!("cannot reach Lark at {base_url}: {e}"))`，区分「host 不可达」vs「凭据错」。

**注意错误处理细节**：飞书的 `tenant_access_token/internal` 即使凭据错误也返回 HTTP 200 + `code!=0`（被现有 `lark_envelope` 证实，util.rs:79-97）。所以第一步只看 `code`，不看 HTTP status。第二步同理。

### 1c. 避免重复：不抽 helper
`lark.rs:143-182` 的 `tenant_token` 有近似逻辑，但它在 `legion-channel`（不同 crate），且带缓存（probe 不需要）。CLI 侧这 ~50 行独立实现是**最简单、最符合分层**的，刻意不跨 crate 抽公共（AGENTS.md：避免为复用而加无谓耦合）。

## 改动 2：`crates/legion-cli/src/setup.rs` — Lark 分支接入校验 + 三选项交互

### 2a. 把 `gather_channels` 改为 `async fn`
当前 setup.rs:1238 是同步 `fn`。两处调用点加 `.await`：
- setup.rs:916（`run_setup` 内）
- setup.rs:1420（`configure_channels_interactive` 内）

其余分支不变（同步代码在 async fn 里正常跑），只有 lark 分支会 `.await` probe。这符合文件里已有的 `async fn` + `maybe_test_connection().await` 先例。

### 2b. Lark 分支（setup.rs:1292-1304）改造
收集完 `app_id` / `app_secret` / `allowlist` 后，**在构造最终 channel JSON 之前**插入校验循环：

```rust
"lark" => {
    let app_id = prompt("Lark app id (cli_…):")?;
    if app_id.is_empty() {
        println!("Skipped: an app id is required.");
        continue;
    }
    let app_secret = gather_channel_secret("Lark app secret", "LARK_APP_SECRET")?;

    // 新增：可选的 base_url prompt（Lark 国际版用 larksuite.com）
    let base_url = prompt_default(
        "Lark base URL (Enter for Feishu China; use https://open.larksuite.com for Lark)",
        "https://open.feishu.cn",
    )?;

    // 连接校验（三选项循环）
    let (app_id, app_secret, base_url, bot_open_id) = loop {
        match probe_lark(&app_id, &app_secret, &base_url).await {
            LarkProbeOutcome { ok: true, bot_name, bot_open_id, .. } => {
                let who = bot_name.as_deref().or(bot_open_id.as_deref()).unwrap_or("bot");
                println!("✓ Lark connection verified (connected as {who}).");
                break (app_id, app_secret, base_url, bot_open_id);
            }
            LarkProbeOutcome { error: Some(reason), .. } => {
                println!("✗ Lark connection test failed: {reason}");
                match select(
                    "What next?",
                    &["Retry", "Save anyway", "Cancel"],
                    0,
                    SelectLayout::Vertical,
                )? {
                    0 => continue,                 // 重试：重新 probe（同参数）
                    1 => break (app_id, app_secret, base_url, None), // 仍保存
                    _ => continue 'channel_loop,    // 放弃：回到 channel 菜单
                }
            }
        }
    };

    let allowlist = gather_dm_allowlist(id, "Lark open_id, e.g. ou_…")?;
    let mut channel = json!({ "appId": app_id, "appSecret": app_secret, "baseUrl": base_url });
    if let Some(bot_open_id) = bot_open_id {
        channel["botOpenId"] = json!(bot_open_id);  // 自动回填，省去用户手填
    }
    with_access(channel, &allowlist)
}
```

**交互细节**：
- 校验放在 `gather_dm_allowlist` **之前**——凭据不对时别浪费用户时间填 allowlist。
- 「放弃」用 `continue 'channel_loop`（需给外层 loop 加 label `'channel_loop`），回到「Add a chat channel?」菜单，不退出整个 setup。
- 成功时把 `botOpenId` 自动回填（`LarkConfig` 已支持该字段，lark.rs:52/194），省去用户手动查 open_id。
- 「重试」用同参数重 probe（用户已填的 app_id/secret/base_url 保留）；如需改参数，走「Cancel」重新进 lark 分支。

### 2c. 给 `gather_channels` 的外层 loop 加 label
setup.rs:1240 的 `loop {` 改为 `'channel_loop: loop {`，供 lark 分支的「Cancel」跳转。

## 改动 3：测试

### 3a. `crates/legion-cli` 目前**没有** wiremock 依赖
确认：`legion-cli/Cargo.toml` 无 `wiremock`。两个选择：
- **(推荐) 不给 CLI 加 wiremock**，probe 的网络逻辑用**单元测试覆盖纯解析部分**：把「解析 tenant_access_token 响应 JSON」「解析 bot/v3/info 响应 JSON」「code!=0 判定」抽成纯函数（接收 `serde_json::Value`），在 `#[cfg(test)]` 里用构造的 JSON 测成功/失败/缺字段三条路径。HTTP 请求本身是 reqwest 标准用法，不需测。
- probe 的端到端（mock server）测试留给未来，因为 CLI 侧加 wiremock 会增加编译面，且 model provider 的 `test_connection` 目前也没测（setup.rs 的测试全是 config 生成/merge，无网络）。

### 3b. 具体测试（setup.rs `#[cfg(test)]` 内）
```rust
#[test]
fn lark_probe_parses_successful_credentials() {
    let body = json!({ "code": 0, "tenant_access_token": "t-xxx", "expire": 7200 });
    let outcome = classify_token_response(&body);
    assert_eq!(outcome.token, Some("t-xxx".into()));
    assert!(outcome.error.is_none());
}

#[test]
fn lark_probe_detects_invalid_secret() {
    let body = json!({ "code": 99991663, "msg": "app secret is not correct" });
    let outcome = classify_token_response(&body);
    assert!(outcome.token.is_none());
    assert_eq!(outcome.error.as_deref(), Some("app secret is not correct"));
}

#[test]
fn lark_probe_parses_bot_info() {
    let body = json!({ "code": 0, "data": { "bot": { "open_id": "ou_bot", "app_name": "MyBot" } } });
    let bot = classify_bot_info(&body);
    assert_eq!(bot.bot_open_id.as_deref(), Some("ou_bot"));
    assert_eq!(bot.bot_name.as_deref(), Some("MyBot"));
}
```
