## 目标

把 slack / discord / lark 三个 socket channel 各自复制的"外层重连骨架"抽成 `util.rs` 里的一个通用函数。这是上一轮分析中唯一没收干净的缝。

## 现状

三个 provider 都有一对几乎同构的函数：

| provider | 外层重连循环 | 单连接处理 |
|---|---|---|
| slack | `socket_loop` (`slack.rs:279`) | `run_socket` (`slack.rs:306`) |
| discord | `gateway_loop` (`discord.rs:286`) | `run_gateway` (`discord.rs:314`) |
| lark | `socket_loop` (`lark.rs:858`) | `run_connection` (`lark.rs:893`) |

外层循环代码完全同构：
```rust
while running.load(Ordering::SeqCst) {
    match open_url(http, cfg).await {
        Ok(url) => { if let Err(e) = run_one(&url, ...).await { warn!(...) } }
        Err(e) => warn!(...);
    }
    if !running.load(Ordering::SeqCst) { break; }
    reconnect_delay().await;
}
```
唯一不同点：(a) 怎么拿 WS URL，(b) 拿到 URL 后怎么处理单条连接，(c) lark 还需要跨重连保活一个 `deduper` 状态。

## 方案

在 `util.rs` 新增一个通用重连循环，用两个回调参数吸收差异：

```rust
/// 外层重连循环：反复"获取 WS URL → 跑一条连接"，直到 `running` 关闭。
/// 三种差异由回调提供：
///   - `open`:   怎么拿一条新连接的 WS URL（HTTP 接口握手）
///   - `serve`:  拿到 URL 后跑一条连接；返回时外层重连
///   - `state`:  跨重连保活的可变状态（lark 的 EventDeduper；其它用 `&mut ()`）
pub(crate) async fn ws_reconnect_loop<Open, Serve, State>(
    channel: &'static str,
    running: &Arc<AtomicBool>,
    state: &mut State,
    open: impl AsyncFn() -> Result<String, String>,
    serve: impl AsyncFnMut(&mut State, String) -> Result<(), String>,
)
```

为什么用 `AsyncFn` / `AsyncFnMut` trait bound（而非裸 `async fn` 指针或 boxed future）：
- `open` 每次调用要重新发 HTTP，需捕获 `&http`/`&cfg` —— `AsyncFn` 天然支持。
- `serve` 需 `AsyncFnMut`，因为 lark 要 `&mut deduper`（回调内 `inbound_tx.send().await`），且要捕获 `cfg`/`inbound_tx`。
- 这是最贴合"channel 只提供'怎么拿 URL'和'怎么处理一帧'"的表达；`AsyncFn` 在 1.85 稳定，1.86 MSRV 可用。

不用 trait object / 不引入新 trait 类型：三个 provider 的 `serve` 闭包各自就地写，签名由通用函数约束，零动态分发。

## 改动文件

1. **`crates/legion-channel/src/util.rs`** — 新增 `ws_reconnect_loop`（约 25 行）。放在已有的 `reconnect_delay` 旁。

2. **`crates/legion-channel/src/slack.rs`** — 删 `socket_loop`，`run_socket` 内联为 `serve` 闭包；保留 `open_socket_url` 作为 `open`。`start` 里 `socket_loop(...)` 调用换成 `ws_reconnect_loop("slack", ...)`。state 用 `&mut ()`。

3. **`crates/legion-channel/src/discord.rs`** — 同理：删 `gateway_loop`，`run_gateway`（含 HELLO/IDENTIFY/heartbeat/select）内联为 `serve`；`fetch_gateway_url` 作为 `open`；`bot_user_id` 在闭包内捕获。state 用 `&mut ()`。

4. **`crates/legion-channel/src/lark.rs`** — `socket_loop` 改为：在循环外创建 `deduper`，调用 `ws_reconnect_loop("lark", &running, &mut deduper, open, serve)`；`serve` 即原 `run_connection`（`deduper` 通过 `AsyncFnMut` 的 `&mut State` 传入）。`open_ws_endpoint` 作为 `open`。

## 不改动的部分

- **telegram / matrix 不纳入**：telegram 是 HTTP 长轮询、matrix 是 `/sync` 长轮询，形状不同（无 WS 连接、无"拿 URL"步骤），强行套同一骨架反而要塞 `()` 占位。保持各自 `poll_updates` / `sync_loop` 原样。
- **`Lifecycle`、`ChannelProvider` trait、`route_inbound_to_runtime` 管线**：完全不动。
- 各 provider 的 `parse_config` / `capabilities` / `send` / 协议解析 / frame codec：完全不动。

## 验证

- 每个改动的 crate 跑 `cargo test -p legion-channel`（现有纯函数单测覆盖 socket_envelope / message_create / frame codec，不受影响）。
- 全量 `cargo build --workspace --all-targets` + `cargo clippy --workspace --all-targets` + `cargo fmt -- --check`。
- 行为保持位等价：重连节奏（`reconnect_delay` 5s）、`running` 关闭即退出、掉线/握手失败的处理路径全部走通用函数，日志语义不变（channel 名仍进 log）。

## 净效果

三个文件各删 ~20 行重复外层循环，`util.rs` 增 ~25 行通用函数；socket channel 此后只需声明"怎么拿 URL + 怎么处理单连接"，外层重连成为通用层职责，与 channel 抽象的整体理念一致。
